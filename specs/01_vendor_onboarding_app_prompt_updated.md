# Prompt 1 — Build the Vendor Onboarding Web App

Build a **working local Indian B2B vendor-onboarding demo** using **Python, Streamlit, SQLite, PyMuPDF, and Gemini (`google-genai`)**. The app must accept vendor details and documents, actually extract and reconcile their contents, apply Python rules, return an explainable decision, draft vendor communication, and retain an audit history. Keep the code straightforward enough to explain in a five-minute live demo.

## Critical separation from Prompt 2

**A separate, one-time script specified in `02_synthetic_dataset_generator_prompt.md` generates test inputs.** Its output is **not part of the application** and must not be bundled, generated, imported, or automatically discovered by the running Streamlit app. In a test, the user reads a generated `form_input.json`, **manually enters its eight values into the Streamlit form**, and **manually uploads its three PDFs**. The app handles them exactly as it would any other uploaded documents.

The only exception is explicit **one-time database fixture setup**, performed **outside the app**: run `python database.py --seed /path/to/sample_data/seed_db_records.json` to load one existing approved vendor and one blocklisted entity needed for duplicate/blocklist tests. The live application never opens the dataset directory. It must **never read `test_scenarios.json`, `expected_outcome`, `expected_validation_failures`, filenames, or vendor IDs to decide an outcome**.

Implement precisely the contracts and policies below, which Prompt 2 mirrors.

Read `GEMINI_API_KEY` from the environment or `.env`; use a documented, configurable Gemini model name. Never embed secrets. Do not add authentication, external APIs for GST/banking, live email sending, data generators, or test-case selectors to the web app.

## 3. Document processing

On the user's Submit action, run these stages in order, showing each actual stage with Streamlit `st.status`/progress and logging timestamps:

1. **Receive and persist** submission metadata and start an execution record.
2. **Read documents**: validate supported file type, integrity, bounded size/pages. For PDFs use PyMuPDF text extraction first; when text is missing or unusable, render pages and use Gemini Vision. Use Vision for uploaded images. For usable digital PDF text, send extracted text to Gemini for structured field mapping.
3. **Classify document by content** into `GST_CERTIFICATE`, `PAN_DOCUMENT`, `BANK_PROOF`, `UTILITY_BILL`, `UNKNOWN` and extract only visibly supported fields. Never pass form fields as purported document evidence, and never infer missing IDs.
4. **Validate** form and document data using deterministic Python checks; show each result and its evidence.
5. **Decide** status from validation rules, not from Gemini's opinion.
6. **Draft** a correction/rejection email for non-approved submissions using a deterministic template (no email sending).
7. **Persist and display** final status, evidence, execution logs, and drafted message.

Use one consistent extracted object per slot:

```json
{
  "upload_slot": "bank_proof",
  "document_type_detected": "BANK_PROOF",
  "is_legible": true,
  "extraction_method": "PDF_TEXT",
  "fields": {
    "legal_name": null,
    "trade_name": null,
    "pan": null,
    "gstin": null,
    "registered_address": null,
    "account_holder_name": "Kovai Precision Components Pvt Ltd",
    "bank_account_number": "12345678901234",
    "ifsc": "HDFC0001234"
  },
  "errors": []
}
```

`extraction_method` is `PDF_TEXT` or `VISION`; use `null` for unavailable fields. Parse Gemini responses as schema-validated JSON; permit one retry for malformed output. Unreadable files, missing API keys, or extraction failures result in **PENDING / review**, never approval or fabricated fields. Preserve extraction errors and use clear messages.

## 4. Deterministic rules and policy

Return a record for each applicable check: `rule_id`, `status` (`PASS`, `WARN`, `FAIL`), `details`, `evidence`, `disposition` (`NONE`, `REVIEW`, `REJECT`). **FAIL does not always mean REJECT.** Use these rule IDs verbatim:

| Rule ID | Finding | Disposition |
|---|---|---|
| `MISSING_REQUIRED_DOCUMENT` | Empty required upload slot | REVIEW |
| `WRONG_DOCUMENT_TYPE` | Content type differs from upload slot | REVIEW |
| `DOCUMENT_UNREADABLE` | Required document not legible or extractable | REVIEW |
| `EXTRACTION_UNAVAILABLE` | Required Gemini/extraction step fails | REVIEW |
| `PAN_INVALID_FORMAT` | PAN not `^[A-Z]{5}[0-9]{4}[A-Z]$` | REVIEW |
| `GSTIN_INVALID_FORMAT` | Invalid state/15-character GSTIN structure | REVIEW |
| `GSTIN_INVALID_CHECKSUM` | Invalid standard GSTIN modulo-36 check character | REVIEW |
| `PAN_GSTIN_MISMATCH` | PAN in GSTIN at zero-based `[2:12]` differs from form PAN or PAN document | REJECT |
| `IFSC_INVALID_FORMAT` | IFSC not `^[A-Z]{4}0[A-Z0-9]{6}$` | REVIEW |
| `IDENTIFIER_MISMATCH` | Form and relevant document disagree on PAN, GSTIN, account number or IFSC (other than the specific PAN/GSTIN rule) | REVIEW |
| `LEGAL_NAME_MISMATCH` | Material disagreement between submitted legal name and GST/PAN legal name | REVIEW |
| `BANK_BENEFICIARY_MISMATCH` | Clearly unrelated individual bank beneficiary for corporate vendor | REJECT; ambiguous discrepancies REVIEW |
| `DUPLICATE_VENDOR` | Exact PAN/GSTIN matches an approved vendor, or bank account matches with corroborating identifying evidence | REJECT |
| `BLOCKLIST_MATCH` | Exact PAN match to internal blocklist | REJECT |
| `FREE_EMAIL_DOMAIN` | Corporate submission uses a common personal email domain | REVIEW |

Use valid Indian GSTIN state codes, structural regex and **correct base-36 checksum calculation**. The 15-character GSTIN embeds its PAN at positions 3–12 (zero-based slice `[2:12]`), has a fixed `Z` at position 14 (index 13), and a check character at index 14. PAN and IFSC syntax checks do not establish official validity.

Normalize casing, whitespace, punctuation and ordinary corporate suffix variants (`Pvt Ltd` versus `Private Limited`) before name comparisons; do **not** treat fuzzy similarity as proof of identity. Reconcile legal and trade/DBA names separately. A bank account whose holder matches the **documented** GST/PAN legal entity but differs from the *submitted* legal name, with consistent trade name, is **PENDING for clarification**, not automatically rejected (Vendor 4). A clear unrelated individual beneficiary for a corporate vendor is **REJECTED** under this explicitly simulated corporate-payee policy (Vendor 3). Explain these policy assumptions in the README.

For duplicate checks, query **only the SQLite `approved_vendors` table**, not prior pending/rejected submission history, so repeated demo cases do not interfere with each other. Prioritize exact PAN/GSTIN matches; do not reject merely because unrelated vendors share a bank account. Blocklist matching is exact PAN. If approved, insert into `approved_vendors` idempotently.

Decision precedence: **any `REJECT` → `REJECTED`; else any `REVIEW` → `PENDING`; otherwise `APPROVED`**. A failed extraction or missing evidence cannot produce approval. Label successful decisions **“Approved under simulated onboarding policy”**. Describe observed problems, never assert proven fraud, verified bank ownership, or government verification.

## 5. SQLite and one-time setup

Create tables: `submissions`, `approved_vendors`, `blocklist`, `execution_logs`. Store form values, extracted JSON, individual rules, status, explanation, follow-up draft, times, and stage/error logs. Use parameterized SQL and safe handling of reruns. Mask bank account numbers in ordinary UI display.

On first start, initialize **empty tables only**. Do **not** auto-load sample data or auto-seed from `sample_data/`. Implement exactly one external setup command:

```bash
python database.py --seed ./sample_data/seed_db_records.json
```

It must read the JSON schema below, insert records idempotently, print what was inserted/already present, and exit. Re-running the seed command must not duplicate rows. The same command may accept another absolute/relative seed JSON path. No seed records should be hardcoded into Python.

```json
{
  "approved_vendors": [{
    "legal_name": "Meridian Technology Services Pvt Ltd",
    "pan": "<actual Vendor 7 PAN>",
    "gstin": "<actual Vendor 7 GSTIN>",
    "bank_account_number": "<actual Vendor 7 account>",
    "ifsc": "<actual Vendor 7 IFSC>"

    "legal_name": "Orion Global Traders",
    "pan": "<actual Vendor 8 PAN>",

  }]

```

The bracketed values describe relationships; the generator outputs concrete strings. The **only** role of this seed file is prepopulating independent SQLite reference tables for two realistic tests. The running app still gets its inputs from the user form/uploads.
